1. Introduction and problem statement

Choosing a wall colour is one of the most common home-improvement decisions, and one of the easiest to get wrong. A small paint chip under shop lighting rarely looks the same as a whole wall in a real room, with its own daylight, shadows and furniture. A wrong choice means buying more paint, repainting, and disappointment.

The project specification identifies four problems:

  • Customers cannot accurately visualise the final painted look.
  • Shade cards do not reflect real room lighting.
  • Wrong choices cause dissatisfaction and repainting costs.
  • No easy, user-friendly preview tool exists for ordinary users.

Smart Wall Paint Visualizer solves this with a browser-based tool. A user uploads a photo of their own room, marks the walls with simple tools, and tries colours, two-tone splits and patterns. The paint is blended so that the photo's own lighting, shadows and wall texture show through, which makes the preview look like paint rather than a flat coloured overlay. Designs can be saved, compared side by side, and downloaded at full resolution.

The same tool supports interior designers and painters during consultations, and paint retailers helping customers decide.

4. System architecture

The application follows a classic three-tier design: an Angular single-page app in the browser, a stateless Express REST API, and MongoDB for data. Images are kept out of the database in object storage and are only reachable through short-lived signed links.

Design decisions

  • Rendering runs in the browser. Recolouring happens on an HTML5 canvas in the user's browser, so changes appear instantly and the server never has to process images per click.
  • Walls are stored as vectors, not images. A wall is a polygon plus brush/eraser strokes in coordinates normalised to the photo (0–1). This keeps saved designs small, fully editable, and re-renderable at any resolution.
  • Feature-based modular code. The Angular app is split into lazy-loaded feature areas (upload, wall selection, studio, admin, …) and the API into routes, controllers, services and middleware, as the specification's structure (§11) suggests.

8. Features in detail

8.1 Uploading a room photo

Users drag in a photo or choose one. The browser checks the type, size and dimensions instantly and shows a preview; the server then checks everything again. Users must confirm that they own the photo, as the project guidelines require. On the server each upload is re-encoded, which removes hidden data such as GPS location, and stored in three sizes: the original (for full-quality downloads), a working copy of at most 2000 px (for fast editing), and a thumbnail.

8.2 Selecting walls

  • Polygon tool: click each corner; close on the first point or press Enter; drag corners afterwards to adjust.
  • Brush and eraser: paint to add awkward areas or remove windows, doors and furniture, with adjustable size.
  • Multiple named walls, each painted independently; rename, delete with undo.
  • Precision aids: zoom and pan (mouse wheel, pinch and two-finger pan on tablets), 100-step undo/redo, adjustable soft edges, keyboard shortcuts.
  • A first-use guide explains the steps the first time someone opens the editor.

8.3 Painting in the studio

Each wall can be painted in one of three ways:

  • Solid colour from the library, favourites, recently used colours, or any custom HEX code.
  • Two-tone: two colours split horizontally or vertically at an adjustable position, like a painted dado line.
  • Pattern: a tile repeated across the wall, with adjustable size and rotation and chosen background and pattern colours.

Finish (matte, satin, glossy), opacity, brightness and edge softness are adjustable per wall. The applied colour's name, code and brand are always shown, and a disclaimer reminds users that real results vary with lighting, screen calibration and wall texture.

8.4 Design variants and comparison

Users can try several ideas on the same photo. A new variant copies the current colours; walls are shared across variants, so editing a wall's shape updates every design. The compare slider shows the original photo, or another design, on one side of a draggable divider.

8.5 Saving, downloading and managing designs

  • Auto-save about one second after the user stops editing, with a visible status (Saving…, All changes saved, Retry).
  • Download as PNG or JPG at the photo's full original resolution, either the painted room or a side-by-side before/after, with an optional caption listing each wall's colours and the disclaimer.
  • My designs shows painted thumbnails with Draft/Saved status; designs can be reopened, renamed, duplicated (including their photos), downloaded and deleted.

8.6 Colour library and favourites

The library groups colours by family and supports search by name, code or HEX, and filters by room and finish. Filters are kept in the page address, so a search can be bookmarked or shared. Each colour has a detail page with HEX/RGB values, finish previews, suitable rooms, related colours and a “Try on my room” button that starts an upload with that colour pre-selected.

9. Realistic rendering method

The quality of the product depends on making painted walls look real. Simply drawing a semi-transparent colour over the photo looks flat and fake, because it hides the shading that tells the eye a wall is three dimensional. The paint engine instead keeps each pixel's shading and replaces only its colour.

Algorithm

  1. Mask. The wall's polygon and brush/eraser strokes are drawn into an alpha mask at the image's resolution. Optional feathering blurs the edge (three passes of a box blur, approximating a Gaussian).
  2. Luminance. Every pixel's brightness is computed in linear light (not raw sRGB values), which is how light actually adds up.
  3. Relative shading. The engine finds the wall's average brightness, then each pixel's shading s relative to that average: shadows have s < 1, highlights s > 1.
  4. Finish. Highlights are flattened for matte (×0.55), kept for satin and boosted for glossy (×1.4).
  5. Recolour. The paint colour is multiplied by the shading and brightness, converted back to sRGB, and mixed with the photo by the mask and opacity.
s = Lpixel / Lwall average
resultlinear = paintlinear × finish(s) × 2brightness / 100
output = mix(photo, toSRGB(result), mask × opacity)

A useful property: on a perfectly evenly lit wall the result is exactly the paint colour, while real photos keep their shadows, light falloff and texture. Two-tone walls choose the colour per pixel by the split line (with a 1-pixel anti-aliased edge); patterns mix the two colours by the tile's coverage.

Performance

Masks and luminance are cached, so changing a colour only re-runs the per-pixel blend, using lookup tables for the sRGB conversions. On a 1600 × 1200 photo a colour change takes about 11–21 ms in Chrome, far inside the specification's target of 300 ms for a 2000 px image (§7). A unit test enforces the 300 ms budget on a 2000 × 1500 image.

Full-resolution export

Downloads re-run the same engine on the full-size original photo instead of the 2000 px working copy, as the specification requires (§8.6). Because walls are stored as vectors, they redraw sharply at any size.

12. Admin panel and analytics

  • Colours: add, edit, remove and restore; bulk import from CSV or JSON with a per-row error report. Changes appear in the public library immediately.
  • Patterns: upload tiles (converted to greyscale so users can tint them), edit and remove.
  • Users: search, change roles, activate or deactivate.
  • Designs and activity: read-only views of all users' designs and a filterable activity log.
  • Settings: maximum upload size, allowed formats, default finish and the disclaimer text, applied immediately.

KPI dashboard

The dashboard shows the four KPIs from the specification (§14) for the last 7, 30 or 90 days and refreshes every 30 seconds: room photos uploaded, designs saved, average session duration (measured in the browser and sent even when the tab closes) and user satisfaction (a 1–5 star rating requested after downloads, at most once a week). It also shows daily trends with a table view, the rating distribution and the most-used colours. The chart colours were checked with a colour-vision-deficiency validator.

Saving brush selections efficiently and keeping them editableStored walls as vector polygons and strokes in normalised coordinates instead of mask images
The test framework (Jest) could not connect to the test database on Node 26Diagnosed a driver handshake problem inside Jest's sandbox and switched API tests to Mocha

17. Future scope

  • AI wall detection: automatic wall segmentation to replace manual selection, with the existing tools for corrections.
  • Lighting simulation: day, evening and warm/cool light previews.
  • Brand integration: catalogue sync with paint manufacturers, “buy this colour” links and quantity estimates from wall area.
  • Mobile and AR: a native app and live camera preview.
  • Sharing and collaboration: share a read-only design link with a client or family member.
  • Performance: move pixel processing to a Web Worker for very large photos on low-end devices.

18. Conclusion and learnings

Smart Wall Paint Visualizer meets the Phase 1 specification as a complete, end-to-end MEAN application: eleven connected pages, a realistic browser-side rendering engine, secure handling of private photos, an admin panel with live KPIs, and 194 automated tests running on every change.

Key learnings

  • Image processing fundamentals: colour spaces, linear light and luminance turned out to be the key to realistic results.
  • Building for real users: undo, auto-save, clear errors, a first-use guide and accessibility matter as much as the core feature.
  • Security by design: validating files by content, signing private links and enforcing ownership on every request.
  • Testing in a real browser finds real bugs: several issues (missing data, timing and keyboard focus problems) only appeared in end-to-end runs and were fixed before release.
  • Working in small, reviewed steps: each feature was built on its own branch and merged through a pull request with automated checks.

19. Appendix: running the project

Requirements

Node.js 18 or later, Docker (for a local MongoDB) and Git.

Steps

git clone https://github.com/novshita/smart-wall-paint-visualizer.git
cd smart-wall-paint-visualizer
docker compose up -d        # MongoDB

cd server && npm install && cp .env.example .env
npm run seed                # colours, patterns, admin account
npm run dev                 # API on http://localhost:5050

cd ../client && npm install && npm start  # app on http://localhost:4200

  • Local admin account (created by the seed): admin@swpv.local / ChangeMe123!. For the live site, admin credentials are provided separately.
  • API documentation: http://localhost:5050/api/docs
